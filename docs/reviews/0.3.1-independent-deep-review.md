## 一、四问直答

### 1. 项目模块是否彻底闭环了？

**核心闭环成立，边缘未闭环。**

| 链路 | 状态 | 依据 |
|---|---|---|
| 任务执行主链（submit → taskfabric → scheduler → quantum → complete/yield） | ✅ 闭环 | 状态机 `canTransition` 覆盖全部合法边；失败级联 `cascadeFailureLocked`；yield→READY→再 acquire 续跑闭环 |
| 反馈链（事件 → 经验/置信 → 调度先验 → 策略） | ✅ 闭环 | `endQuantumOutcome` → `tracker.End` + attribution；`ConfidenceSource` 回填候选 |
| 知识链（蒸馏 → store → 检索 → 回注） | ⚠ 基本闭环 | 跨租户 **写**已在本批封堵；但 `UpdateStatus`/`Promote`/`GetRepresentation` 仍无租户维度（F-05） |
| 事件环（append → subscribe → retention/archive） | ✅ 闭环（serve） | `CompactableStoreWithArchive` 已接；但 SDK / arena 私有实例未接 trim（F-14） |
| **MCP 工具链（SDK 路径）** | ❌ **断裂** | stdio 连接后立即 cancel 上下文 → 子进程被杀，`WithMCP` 实际不可用（**F-02**） |
| **evolution v2（CandidatePipeline）** | ❌ 未闭环 | 生产零装配，`ProfileStore.SetStable` 永不执行（F-12，设计保留） |
| **LLM 流式** | ❌ 未闭环 | `Agent.Stream` 为"跑完再分块回放"；底层 `GenerateStream` 零生产调用（F-16） |
| **peer 通信（agentipc）** | ⚠ 边界内可用 | 无 ACL/无死信重试（已文档化为单租户 v1 边界） |

**结论**：作为"任务执行 + 知识 + 记忆"的 agent runtime，主干闭环成立且质量高；但 MCP stdio 路径存在实锤断裂，evolution v2 / 流式属未完成能力储备。

### 2. 能否发布 0.3.1？

**可以有条件发布，但必须先过两点：**

1. ❌ **阻塞项（硬）**：`make ci` 的 `ci-freeze` 目标会红——`scripts/check_convergence_freeze.sh` 因 `docs/convergence/freeze-manifest.txt` 不存在而 `exit 1`（F-01）。发布前必须建清单或移除该门禁。

满足上述后，**单租户定位下可以发布**。

### 3. 0.3.1 是否足够稳定？

- **单租户 / 生产运维场景：是。** 证据链：129 包 short 全绿、核心包 `-race` clean、gofmt clean、goleak 门禁 + soak harness 成型、约 40 项 panic/泄漏修复均带锁定测试、HTTP panic 守卫 + request-ID 归因就位。

### P1 — 高

#### F-02　SDK MCP stdio：连接后立即取消上下文 → 子进程被杀 🆕
- **位置**：`sdk/sdk.go:482-485`
  ```go
  connectCtx, connectCancel := context.WithTimeout(context.Background(), 30*time.Second)
  client, err := mcp.ConnectStdio(connectCtx, conn.Name, conn.Command, conn.Args)
  connectCancel() // ← 立刻取消
  ```
  与 `internal/mcpclient/stdio.go:47`
  ```go
  cmd := exec.CommandContext(ctx, command, args...)
  ```
- **根因**：`exec.CommandContext` 的既定语义是"ctx 一旦 done 即 Kill 子进程"。此处 ctx 在 `ListTools` 之前就被取消，`Start()` 注入的 `watchCtx` goroutine 会杀掉刚启动的 MCP 子进程，随后 `client.ListTools`（`sdk.go:490-497`）读到 stdout EOF → "connection closed" → `New()` 报错。
- **可达性**：`sdk/sdk.go:50` 导入 `internal/mcpclient` 为 `mcp`；`WithMCP`（`sdk/options.go:582`）与 `tools.mcp` 配置（`sdk/config.go:454-473`）都会进入 `wireMCPClients`。**仓库无覆盖该路径的测试**（`mcpclient` 测试均走 mock/直接构造 transport，绕过 `ConnectStdio`；`examples` 用 `context.Background()` 故不复现）。
- **影响**：README 宣称的 "MCP Ready" 在 SDK 路径上不成立。
- **建议**：`ConnectStdio` 不应把"连接超时 ctx"与"进程生命周期 ctx"合一。改为：连接期用带超时 ctx 做启动，进程 lifetime 绑定到一个独立的（由 `Client.Close` 取消的）ctx；或让 `Client` 持有并 cancel 该 lifetime ctx。

#### F-03　Restore 折叠顺序依赖时间戳排序，终态任务可被"复活"为 READY
- **位置**：`internal/fabric/task/restore.go:105-154,279-295` + `internal/ares_events/memory_store.go:188-196` + `internal/ares_events/pg_store.go:242`
- **证据**：`ReadAll` 仅按 `Timestamp` 排序（memory 用**非稳定** `sort.Slice`；PG `ORDER BY created_at` 单键，无次级键）；而 `foldRestoreEvent` 对非 `created` 事件按 `rest` 的到达顺序逐条覆盖状态：
  ```go
  case ...Checkpointed, ...Completed, ...Failed, ...Expired:
      ...
      switch state := TaskState(...); state {
      case StateCompleted, StateFailed: t.State = state
      default:                          // 含 SUSPENDED / READY
          t.State = StateReady; t.Owner = ""; t.Lease = nil
      }
  ```
  若同一任务的 `task.checkpointed`（state=SUSPENDED）因等时间戳排到 `task.completed` **之后**折叠，`completed` 任务会被重置为 READY → **重启后重复执行**，违反文件头"终态任务绝不复活"的契约（`restore.go:82-84`）。
- **放大因素**：`fabric_events.go:250-251` 明确允许 must-persist 事件**乱序落盘**（`persisting must-persist event out of causal order`）。
- **关键点（修复线索）**：事件结构**已有** `Version` 字段且按 stream 单调（`memory_store.go:84 event.Version = startVersion + versionCounter`），但 `ReadAll` **没有用它做 tie-break**；`restore.go:236` 的注释声称"restore folds events by task id, not by position"，与实现不符。
- **触发条件**：需同一任务的两个事件时间戳相等（测试注入时钟 / 粗粒度时钟 / 极短间隔）。生产中纳秒级时间戳通常互异，故**概率低但真实**，且是数据正确性问题。
- **建议**：`ReadAll` 增加 `(Timestamp, Version)` 稳定排序；并在 `foldRestoreEvent` 中对 `COMPLETED/FAILED` 做**吸收态保护**（终态不可被后续非终态覆盖），双保险。

#### F-04　心跳间隔下限 5s 与可配置 TTL 不匹配 → 活跃量子可能被 requeue
- **位置**：`internal/kernel/scheduler_execute.go:386-389`
  ```go
  interval := s.ttl / 3
  if interval < 5*time.Second { interval = 5 * time.Second }
  ```
  与 `internal/kernel/scheduler.go:234-239`（`WithTTL` 接受任意正值）、`cmd/ares/peer_assembly.go:163-167`（YAML `kernel.lease_ttl` 直接透传，注释自述用于 chaos/recovery demo 缩短租约）。
- **影响**：当 `kernel.lease_ttl < 5s` 时，**首次心跳(5s)晚于租约到期**，recovery 会把仍在运行的量子 requeue。epoch fencing 能阻止重复**提交**，但任务副作用/工时可能重复。
- **建议**：校验 `ttl >= 3*interval`，或让心跳间隔自适应（如 `min(ttl/3, ...)` 且保证 `interval < ttl`），TTL 过小时拒绝启动并报错。

#### F-05　知识库三方法缺租户维度 → 知道 ID 即可跨租户操作 🆕
- **位置**：接口 `internal/knowledge/store.go:62-66`（`UpdateStatus(ctx, id, status)`、`Promote(ctx, id, q)`）；`GetRepresentation(ctx, objectID, model)`（同文件 `:49-50`，`Representation` 无 Namespace 字段）。
- **证据**：三后端一致按 ID 直操作，无 namespace 谓词：
  - memory：`store/memory/store.go:384-393`（UpdateStatus）、`:397`（Promote）
  - sqlite：`UPDATE akf_objects SET status=? WHERE id=?`（`store/sqlite/store.go:629`）、`:644`
  - postgres：`WHERE id=$2` / `WHERE id=$1`（`store/postgres/store.go:628,643`）
  - `GetRepresentation`：sqlite `:365` / postgres `:373`（`WHERE object_id=? AND model=?`，无 namespace）
- **影响**：跨租户改状态、改质量、读向量。与已修的 `Save` 缺口同源，但本批未覆盖。
- **补充**：`Query/ListByStatus/HybridSearch` 在 `namespace==""` 时**全租户扫描**（memory `:136,364`；sqlite `:240`；postgres `:196`）——隔离完全依赖调用方自觉，属脆弱契约。
- **建议**：为这四个方法补 `tenantID`（或 namespace）参数并在三后端加谓词；空 namespace 应 fail-closed（至少对跨租户读）。

#### F-06　RLS 全禁用，无第二道防线 📌
- **位置**：`internal/storage/postgres/migrate.go`（`DROP POLICY IF EXISTS` + `DISABLE ROW LEVEL SECURITY`；以表 owner 连接、owner 默认绕过策略、且无 `FORCE RLS`、从不绑定 `app.tenant_id`）。
- **影响**：租户隔离 100% 依赖每条 SQL 手写 `tenant_id` 谓词；任何一处漏写即跨租户泄露，无兜底。
- **建议**：`ExecWithTenant/QueryWithTenant`（当前零生产调用）落地前，至少对全部 repository 的 SQL 做一次 `tenant_id` 谓词审计并固化为测试。
