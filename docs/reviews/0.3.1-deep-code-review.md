## 三、深度代码审查发现

### 严重问题 (P0)

#### F-01: 收敛冻结清单文件缺失

**位置**：`docs/convergence/freeze-manifest.txt`
**问题**：`scripts/check_convergence_freeze.sh` 依赖的 `docs/convergence/freeze-manifest.txt` 文件不存在，冻结检查脚本直接 `exit 1`。
**影响**：架构报告中声称"已修复——manifest 现含 `agentruntime`，freeze-check OK"是**不准确的**——文件从未被创建或已被意外删除。
**修复建议**：
- 要么创建 `docs/convergence/freeze-manifest.txt` 文件并维护 `examples` 和 `internal` 的顶层目录清单
- 要么删除 `check_convergence_freeze.sh` 脚本和相关引用，不再声称冻结检查通过

#### F-02: 多租户隔离的 RLS 策略被禁用后的无第二道防线

**位置**：`internal/storage/postgres/migrate.go` 及各 repository
**问题**：根据架构报告（7.5节），六条装饰性 RLS 策略已改为 `DISABLE ROW LEVEL SECURITY` + `DROP POLICY IF EXISTS`。应用以表 owner 连接（无 `FORCE ROW LEVEL SECURITY` 时 owner 完全绕过策略），且从不绑定 `app.tenant_id` GUC。租户隔离因此 100% 依赖每条 SQL 手写 `tenant_id` 谓词。
**影响**：任何一条 SQL 漏写 `tenant_id` 谓词，就是跨租户数据泄露。虽然已知的漏写已修复（`conversation_repository.GetByID`），但这是一个系统性风险，没有第二道防线。
**修复建议**：在 0.3.1 发布前，至少完成以下一项：
- 对所有 repository 的 SQL 做 grep 审计，确认每条查询都包含 `tenant_id` 谓词
- 或者恢复 RLS 策略并使用非 owner 角色连接数据库
- 或者在未来版本中实现 `ExecWithTenant` / `QueryWithTenant`（当前零生产调用）

### 中等问题 (P1)

#### F-03: `Store.UpdateStatus` 和 `Store.Promote` 缺少租户隔离

**位置**：`internal/knowledge/store/memory/store.go:384-415`
**问题**：`UpdateStatus` 和 `Promote` 方法按 ID 直接操作内存对象，**不检查 tenant/namespace**。其他方法（Get/Delete/Search）都有租户隔离检查，但这两个方法没有。

```go
// UpdateStatus — 没有 tenantID 参数，直接按 ID 操作
func (s *Store) UpdateStatus(_ context.Context, id string, status knowledge.ObjectStatus) error {
    obj, ok := s.objects[id]  // 无 namespace 检查
    // ...
}

// Promote — 同样没有 tenantID 参数
func (s *Store) Promote(_ context.Context, id string, q *knowledge.Quality) error {
    obj, ok := s.objects[id]  // 无 namespace 检查
    // ...
}
```

**影响**：任何租户的对象状态可以被另一个租户的操作修改（如果它们知道对象 ID）。
**修复建议**：给 `UpdateStatus` 和 `Promote` 的接口签名增加 `tenantID` 参数，并在操作前验证对象 namespace 匹配。

#### F-04: `MemoryEventStore.events` 切片无界增长

**位置**：`internal/ares_events/memory_store.go:99`
**问题**：全局 `s.events` 切片持续 append，仅在 `TrimBefore` 被调用时才会清理。如果没有配置 compaction/trim 循环（如 PG 模式才配 `eventsRetentionCleanerFor`），内存模式下 events 切片会无界增长。
**影响**：长时间运行的 serve 进程在内存 EventStore 模式下会 OOM。
**修复建议**：
- 在 `MemoryEventStore` 中增加最大事件数上限，达到后自动触发压缩或丢弃旧事件
- 或者在文档中明确标注内存模式仅用于开发/测试，不用于长期运行

#### F-05: `StallDetector` 不是线程安全的

**位置**：`internal/agentruntime/session.go:249-266`
**问题**：`StallDetector` 的注释明确说"one detector belongs to one wait loop, and that loop must be the only goroutine touching it (no lock)"，但 `consecutive` 字段是非原子的 int，如果使用方意外从多个 goroutine 调用 `Stalled`，会产生 data race。
**影响**：虽然按当前设计不会被多 goroutine 使用，但缺少防御性编程。
**修复建议**：将 `consecutive` 改为 `atomic.Int32` 或加 mutex，作为防御性编程。

#### F-06: `TokenBucketLimiter` 的 `Wait` 方法在极高并发下可能有精度问题

**位置**：`internal/ares_ratelimit/token_bucket.go:55-91`
**问题**：`Wait` 方法计算 `waitTime` 后释放锁再 sleep，多个等待者可能计算出相同的 `waitTime`，在精确的 token 补充时刻同时唤醒。
**影响**：thundering herd 风险（虽然注释声称已避免），在高并发下可能多个等待者同时争抢同一个 token。
**修复建议**：考虑引入随机 jitter 或使用条件变量来精确唤醒。

### 低优先级问题 (P2)

#### F-07: `FailoverClient.GenerateStream` 存在 timer 泄露风险

**位置**：`internal/llm/failover.go:372-433`
**问题**：在 `timer.Stop()` 成功路径中需要 drain `timer.C`，但在 `case <-ctx.Done()` 分支只调用了 `timer.Stop()` 而没有 drain。如果 timer 在同一时刻 fire，`timer.C` 中的值不会被消费。
**影响**：timer goroutine 不会被立即回收，但在 Go 1.23+ 中 `time.NewTimer` 的行为已优化，实际影响很小。
**修复建议**：在 `ctx.Done()` 分支也加 `if !timer.Stop() { <-timer.C }`（需要 select default 防止阻塞）。

#### F-08: `GlobalRegistry` 已废弃但仍然存在

**位置**：`internal/tools/resources/core/registry.go:377-413`
**问题**：`GlobalRegistry` 及其包级函数 `Register` / `Get` / `List` / `Execute` 已标记为 `Deprecated`，但仍然存在。注释说"no production caller invokes Register"，但如果有人误用会产生非预期行为。
**影响**：低风险，但增加了代码维护负担和误用可能。
**修复建议**：在 0.4.0 中删除这些废弃 API。

#### F-09: `ares_security` 部分核心 API 仅测试可达

**位置**：`internal/ares_security/`
**问题**：`VerifyJWT` / `Wrap` / `SanitizeJSON` 仅被测试调用，生产路径用 `Verify` 直连。这意味着这些 API 没有在生产中被验证过。
**影响**：低风险——功能已被测试覆盖，只是缺少生产验证。
**修复建议**：在后续版本中统一安全模块的使用路径。

#### F-10: LLM streaming 路径零生产调用

**位置**：`internal/llm/failover.go:298-466`
**问题**：`GenerateStream` 方法已实现并测试，但生产代码无调用方。
**影响**：能力储备但未验证。
**修复建议**：要么在 serve 中接入 streaming，要么在文档中标注为未接生产。

#### F-11: `evoapi` 遗留门面仅 examples 引用

**位置**：`internal/evoapi/`
**问题**：仅被 examples 引用，计划在 v0.5.0 移除。
**影响**：增加了代码维护负担。
**修复建议**：按计划在 v0.5.0 删除。

#### F-12: `fabric.go` 中 `Checkpoint` 字段的 `any` 类型缺少安全克隆

**位置**：`internal/fabric/task/fabric.go:272-273`
**问题**：`Task()` 方法返回 task 快照时，`Checkpoint (any)` 字段被故意 aliased（注释说明"may hold arbitrary un-cloneable types"）。如果 Checkpoint 实现内部可变且被外部直接修改，可能产生 race。
**影响**：低风险——fabric 只替换整个 Checkpoint 指针，从不通过旧指针修改。但这是一个需要靠约定维持的不变量。
**修复建议**：在注释中更明确地标注这个不变量，或者考虑为 Checkpoint 定义一个 `Cloneable` 接口。

#### F-13: `memory_store.go` 中 `notifySubscribers` 在持锁状态下发送

**位置**：`internal/ares_events/memory_store.go:302-321`
**问题**：`notifySubscribers` 在 `Append` 的 `s.mu.Lock()` 持锁路径中被调用（通过 `prepared` 循环）。虽然 channel send 是 non-blocking 的（`select...default`），但遍历 subscribers 切片是在锁内完成的。
**影响**：如果 subscribers 列表很大，会延长锁持有时间。当前 subscribers 通常不会太多（调度器+compile coordinator），所以实际影响很小。
**修复建议**：可以考虑在释放锁后批量通知（拷贝 subscribers 切片），但这会增加代码复杂度，当前可接受。

## 七、总结

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构闭环 | ⭐⭐⭐⭐⭐ | 四条数据流完整闭环，架构不变量有测试锁定 |
| 代码质量 | ⭐⭐⭐⭐☆ | 注释详尽，错误处理规范，个别防御性编程缺失 |
| 并发安全 | ⭐⭐⭐⭐⭐ | 锁策略清晰，原子操作正确，panic 边界完整 |
| 测试覆盖 | ⭐⭐⭐⭐☆ | 129 包全绿，架构测试锁定，个别边缘 case 缺失 |
| 安全性 | ⭐⭐⭐⭐☆ | JWT/RBAC/租户隔离基本完整，RLS 禁用是系统性风险 |

**最终结论**：ARES 0.3.1 的架构收敛工作质量很高，四条数据流闭环完整，核心执行路径（agentruntime → kernel → fabric → cognition）设计精良。主要风险在于冻结清单缺失（F-01）和多租户隔离的系统性风险（F-02）。修复 F-01 后可以发布。F-02 虽然不阻塞发布，但建议在 0.3.2 中优先解决。
