## 🔍 详细 Review

### 1. M1: 多 Agent 协作模式 (`internal/agentipc/collaboration.go`)

#### ✅ 优点

**1.1 委托模式设计清晰**
```go
func (b *Bus) DelegateToSpecialist(ctx context.Context, delegator, specialist, taskID, specialization string, payload any, timeout time.Duration) (*Message, error)
```
- 使用现有的 `Request/Reply` 原语，不破坏 IPC 层次
- 明确的参数校验（specialist、specialization 不能为空）
- 超时控制合理

**1.2 流水线模式实现简洁**
```go
type Pipeline struct {
    bus     *Bus
    stages  []string
    timeout time.Duration
}
```
- 严格的顺序执行：前一个 stage 的结果作为下一个的输入
- 失败立即停止并返回错误
- `NewPipeline` 构造函数防御空 stages

**1.3 编排模式并发安全**
```go
func (b *Bus) Orchestrate(...) ([]OrchestrationResult, error) {
    var wg sync.WaitGroup
    wg.Add(len(workers))
    for i, worker := range workers {
        go func() { defer wg.Done(); ... }()
    }
    wg.Wait()
    return results, nil
}
```
- goroutine 泄漏防护：`defer wg.Done()`
- worker 变量捕获正确（`i, worker := i, worker`）
- 结果按顺序存储，便于调用方聚合

#### ⚠️ 改进建议

**1.4 Pipeline 缺乏并行优化**
```go
// 现状：严格串行
for _, stage := range p.stages {
    reply, err := p.bus.Request(ctx, from, stage, "pipeline-stage", payload, p.timeout)
}
```
**建议**: 添加 DAG-aware 版本，无依赖的 stage 可并行执行。

**1.5 Orchestrate 缺乏结果聚合策略**
```go
// 现状：返回所有结果，调用方自行聚合
type OrchestrationResult struct {
    Worker string
    Reply  *Message
    Err    error
}
```
**建议**: 提供常见聚合策略：
- Majority Vote（多数投票）
- Best Score（最优评分）
- First Success（首个成功）

### 2. M2: Evolution-Runtime 深度集成

#### ✅ 优点

**2.1 策略源解耦设计优秀**
```go
type SpawnPolicySource interface {
    ActiveSpawnPolicy(ctx context.Context) (SpawnPolicy, error)
}
```
- aresrecovery 不依赖 evolution 包，通过接口解耦
- 方便测试：可以用 stub 实现
- 方便替换：不同场景可用不同策略源

**2.2 SpawnPolicy 字段设计合理**
```go
type SpawnPolicy struct {
    Enabled bool
    MaxConcurrent int
    PreferredCapabilities []string
}
```
- `Enabled` 控制开关（population-down 阶段有用）
- `MaxConcurrent` 防止资源耗尽
- `PreferredCapabilities` 引导 spawn 类型

**2.3 EvolutionAwareQuotaManager 动态调整**
```go
func (m *EvolutionAwareQuotaManager) Apply(ctx context.Context) error {
    policy, err := m.source.ActiveQuotaPolicy(ctx)
    // ...
    return m.agents.UpdateResourceBudget(policy.Budget)
}
```
- 幂等设计：可安全重复调用
- 错误传播清晰

**2.4 EvolutionAwareIPC 压缩策略**
```go
type IPCProtocolPolicy struct {
    Encoding string  // "json" or "json+gzip"
    MinCompressSize int
}
```
- 小 payload 不压缩，避免 overhead
- 向后兼容：默认 `json` 编码

#### ⚠️ 改进建议

**2.5 Spawn 数量检查有竞态风险**
```go
if policy.MaxConcurrent > 0 && len(s.agents.Agents()) >= policy.MaxConcurrent {
    return nil, ErrSpawnLimitReached
}
```
**问题**: `len(s.agents.Agents())` 和实际 spawn 之间存在竞态窗口。
**建议**: 使用原子计数或 CAS 操作确保精确限制。

**2.6 IPC 压缩率自适应缺失**
**建议**: 根据历史消息大小动态调整 `MinCompressSize`。

### 3. M3: 可解释性与人工反馈

#### ✅ 优点

**3.1 EvolutionTracer 自动检测突破/退化**
```go
delta := (bestScore - last) / last
snap.Breakthrough = delta > 0.20
snap.Regression = delta < 0
```
- 阈值可配置（当前硬编码 20%）
- 双向检测：突破和退化

**3.2 FeedbackStore 线程安全且支持更新**
```go
func (s *FeedbackStore) Add(fb HumanFeedback) {
    if idx, ok := s.byCandID[fb.CandidateID]; ok && idx < len(s.entries) {
        s.entries[idx] = fb  // 替换而不是追加
        return
    }
    // ...
}
```
- Latest wins 语义合理
- 防止重复 reviews 无限增长

**3.3 CombinedFitness 权重可调**
```go
func CombinedFitness(autoScore, humanRating float64) float64 {
    return 0.3*autoScore + 0.7*humanRating
}
```
- 初期重人工（0.7），后期重自动（可调）
- 清晰的设计意图

**3.4 Dashboard API 设计规范**
```go
// GET /evolution/trajectory
func (a *APIv2) handleEvolutionTrajectory(w http.ResponseWriter, r *http.Request)

// POST /evolution/feedback
func (a *APIv2) handleEvolutionFeedback(w http.ResponseWriter, r *http.Request)
```
- RESTful 风格
- 输入校验充分（candidate_id 必填）
- 错误响应统一格式

#### ⚠️ 改进建议

**3.5 Trajectory 数据量可能过大**
**建议**: 添加分页或时间范围过滤。

**3.6 Feedback 缺少签名验证**
**建议**: 生产环境需要认证（谁提交的 feedback？）。

### 4. M4: 全局观测与调试

#### ✅ 优点

**4.1 GlobalTracer 三种 Span Kind 覆盖完整**
```go
const (
    SpanTask    SpanKind = "task"
    SpanAgent   SpanKind = "agent"
    SpanMessage SpanKind = "message"
)
```
- 完整追踪 Task → Agent → Message 链路
- ParentID 支持父子关系（如 message 关联到 task）

**4.2 Sandbox Replay 设计巧妙**
```go
type SandboxEvent struct {
    Type string  // "task.create", "task.acquire", "agent.spawn", ...
    TaskID string
    AgentID string
}
```
- 脚本化事件序列，便于复现
- 每个事件后记录 Outcome，便于验证

**4.3 Simulate 预测能力**
```go
func (s *Sandbox) Simulate(ctx context.Context, deadAgentID, taskID string) (*SimulationResult, error)
```
- 离线模拟 agent 死亡后的恢复行为
- 验证 "Agent death ≠ Task death" 不变量

**4.4 时钟注入支持测试确定性**
```go
func (t *GlobalTracer) WithClock(now func() time.Time) *GlobalTracer
func (s *Sandbox) WithClock(now func() time.Time) *Sandbox
```
- 便于单元测试（无需真实等待）

#### ⚠️ 改进建议

**4.5 GlobalTracer 内存无上限**
```go
type GlobalTracer struct {
    mu    sync.Mutex
    spans map[string]*TraceSpan
    order []string
    max   int  // 0 = unlimited
}
```
**现状**: 默认无上限，长时间运行可能内存增长。
**建议**: 添加 LRU 淘汰或 TTL 清理。

**4.6 Sandbox 缺乏持久化**
**建议**: 支持导出/导入 replay 脚本，便于离线分析。

## 🎯 关键亮点

### 1. 设计一致性
所有 Evolution-aware 组件遵循相同模式：
```
Interface (Source) → Wrapper → Existing Primitive
```
- `SpawnPolicySource` → `EvolutionAwareSpawner` → `agentfabric.Fabric.Spawn`
- `QuotaPolicySource` → `EvolutionAwareQuotaManager` → `agentfabric.Fabric.WithResourceBudget`
- `IPCProtocolPolicySource` → `EvolutionAwareIPC` → `agentipc.Bus.Send`

这种一致性降低了维护成本。

### 2. 向后兼容
- 所有新组件都有 nil-safe 处理
- Dashboard API 在 provider 未连接时返回空列表而非 500
- IPC 压缩策略默认关闭（`WireJSON`）

### 3. 测试友好
- Clock injection 使时间相关测试确定性化
- Interface-based design 方便 mock
- Sandbox 提供离线测试环境
