### P0-1: Leader Agent Stop/Start 竞态 Panic

**文件**: `internal/agents/leader/agent.go:680`

```go
// 现状：RLock 读 stopCh，但 channel close 在另一 goroutine 可能发生
func (a *leaderAgent) checkAgentRunning() error {
    a.mu.RLock()           // RLock 不保护 channel close
    defer a.mu.RUnlock()
    select {
    case <-a.stopCh:       // ← 若此时 Stop() 关闭 channel 会 panic
        return errors.ErrAgentNotRunning
    default:
    }
}
```

**触发场景**: 服务重启时快速 Start/Stop 循环

**修复方案**:
```go
type leaderAgent struct {
    stopped atomic.Bool  // 替代直接读取 channel
}

func (a *leaderAgent) checkAgentRunning() error {
    if a.stopped.Load() {
        return errors.ErrAgentNotRunning
    }
    return nil
}
```

**验证测试**:
```go
func TestLeaderAgent_StartStopRacing(t *testing.T) {
    agent := NewTestAgent()
    var wg sync.WaitGroup
    
    for i := 0; i < 100; i++ {
        wg.Add(2)
        go func() {
            defer wg.Done()
            agent.Start(context.Background())
        }()
        go func() {
            defer wg.Done()
            agent.Stop(context.Background())
        }()
    }
    wg.Wait()
    // 验证无 panic、无 goroutine 泄漏
}
```

### P0-2: Distillation Goroutine 泄漏

**文件**: `internal/ares_memory/distillation/distiller.go:147,197`

**问题**:
```go
type Distiller struct {
    distillWg   sync.WaitGroup  // 无状态追踪，panic 后 Done() 永不调用
    distillEg   *errgroup.Group // 无停止机制
}
```

**后果**: 
- 多次调用 `Start()` 累积 goroutine → OOM
- 任何 panic 导致 `WaitGroup` 永久阻塞

**修复方案**:
```go
type distillerState struct {
    mu      sync.Mutex
    running bool
    wg      sync.WaitGroup
}

func (d *Distiller) Start(ctx context.Context) error {
    d.state.mu.Lock()
    defer d.state.mu.Unlock()
    if d.state.running {
        return fmt.Errorf("already started")
    }
    d.state.running = true
    // ... 启动逻辑，确保 panic recovery
}
```

**验证测试**:
```go
func TestDistiller_GoroutineLeak(t *testing.T) {
    d := NewDistiller(...)
    
    initialCount := runtime.NumGoroutine()
    
    for i := 0; i < 50; i++ {
        d.Start(ctx)
        time.Sleep(10 * time.Millisecond)
        d.Stop()
    }
    
    finalCount := runtime.NumGoroutine()
    if finalCount > initialCount+5 {
        t.Fatalf("goroutine leak: %d -> %d", initialCount, finalCount)
    }
}
```

### P0-3: Workflow Scheduler 错误传播遗漏

**文件**: `internal/workflow/scheduler.go:130-145`

```go
func (s *Scheduler) OnNodeFailed(id NodeID) {
    s.completed[id] = true
    for _, index := range s.outgoing[id] {
        edge := s.spec.Edges[index]
        s.markInactive(index)
        if edge.Kind == EdgeDataDependency {
            s.pending = appendUniqueNode(s.pending, edge.To)
        }
    }
}
```

**问题**: 节点 B 依赖 A1 和 A2，仅 A1 失败时 B 不会被正确标记为失败

**修复方案**: 引入 in-degree counter
```go
type Scheduler struct {
    inDegree    map[NodeID]int
    failedUpstream map[NodeID]bool
}

func (s *Scheduler) OnNodeFailed(id NodeID) {
    s.failedUpstream[id] = true
    for _, index := range s.outgoing[id] {
        to := s.spec.Edges[index].To
        s.inDegree[to]--
        if s.inDegree[to] == 0 && s.hasAnyFailedUpstream(to) {
            s.propagateFailure(to)
        }
    }
}
```

**验证测试**:
```go
func TestScheduler_MultiUpstreamFailure(t *testing.T) {
    // A1 -> B <- A2
    spec := createDAGWithDiamond()
    scheduler := NewScheduler(spec)
    
    scheduler.OnNodeCompleted("A1")  // 完成一个上游
    scheduler.OnNodeFailed("A2")     // 另一个上游失败
    
    // B 应该被标记为失败而不是 pending
    assertFailurePropagated(t, scheduler, "B")
}
```

### P0-4: 多租户数据隔离风险

**文件**: 所有 repository（`knowledge_repository.go`, `experience_repository.go` 等）

**现状**:
```sql
-- 硬编码表名，依赖 WHERE tenant_id = $1 过滤
SELECT * FROM experiences_1024 WHERE tenant_id = $1
```

**风险**: 
- 索引缺失或查询计划异常时可能跨租户返回数据
- 不符合零信任安全模型

**修复方案** (选择其一):

**方案 A: Schema per Tenant**
```sql
CREATE SCHEMA IF NOT EXISTS tenant_123;
CREATE TABLE tenant_123.experiences_1024 (...);
-- 查询时动态切换 schema
```

**方案 B: 强制索引提示**
```sql
SELECT /*+ INDEX(experiences experiences_tenant_idx) */ 
       * FROM experiences_1024 
WHERE tenant_id = $1 AND ...
```

**方案 C: 应用层强制校验**
```go
func (r *KnowledgeRepository) Query(ctx, tenantID, ...) {...}
// 在每处查询前强制检查 tenant_id 参数非空
if tenantID == "" {
    return nil, errors.ErrTenantRequired
}
```

**验证测试**:
```go
func TestMultiTenant_DataIsolation(t *testing.T) {
    t1 := createTenant("tenant-1")
    t2 := createTenant("tenant-2")
    
    // 并发写入
    var wg sync.WaitGroup
    for i := 0; i < 50; i++ {
        wg.Add(2)
        go func() {
            defer wg.Done()
            t1.store.Write(makeRecord("t1-data"))
        }()
        go func() {
            defer wg.Done()
            t2.store.Write(makeRecord("t2-data"))
        }()
    }
    wg.Wait()
    
    // 验证隔离
    t1Records := t1.store.Query(...)
    t2Records := t2.store.Query(...)
    
    for _, r := range t1Records {
        assert.NotContains(t, r.Content, "t2-data")
    }
    for _, r := range t2Records {
        assert.NotContains(t, r.Content, "t1-data")
    }
}
```

### P1-2: Goroutine 生命周期管理不统一

**现状统计**:
```
总 goroutine spawn: 39 处
纳入 errgroup: 15 处
未跟踪: 24 处
```

**未跟踪的关键位置**:
- `llm/client.go` — HTTP request goroutine
- `ares_mcp/transport_server.go:216` — serve loop
- `dashboard/orchestrator.go:125` — WebSocket 广播

**修复方案**: 统一 Worker Pool
```go
type WorkerPool struct {
    wg     sync.WaitGroup
    tasks  chan func()
}

func (wp *WorkerPool) Go(fn func()) {
    wp.wg.Add(1)
    go func() {
        defer wp.wg.Done()
        fn()
    }()
}
```

### P1-4: Heartbeat Map 内存泄漏

**位置**: `internal/ares_protocol/ahp/heartbeat.go:275`

```go
func (hm *HeartbeatMonitor) RecordHeartbeat(agentID string) {
    hm.mu.Lock()
    defer hm.mu.Unlock()
    hm.lastHeartbeat[agentID] = time.Now()  // 无限增长

```

**修复**:
```go
const heartbeatTTL = 5 * time.Minute

func (hm *HeartbeatMonitor) cleanupExpired() {
    hm.mu.Lock()
    defer hm.mu.Unlock()
    cutoff := time.Now().Add(-heartbeatTTL)
    for id, last := range hm.lastHeartbeat {
        if last.Before(cutoff) {
            delete(hm.lastHeartbeat, id)
        }
    }
}
```

## 🎯 结论

**不建议立即发布 v0.3.0**，原因：

1. **存在 4 个 Critical 问题**，其中 P0-1 和 P0-2 可能导致生产环境崩溃
2. **测试覆盖不足**，缺少 stress test 和 long-run test
3. **安全隔离风险**，多租户数据泄露可能造成严重后果

**建议行动**:
1. 立即启动 P0 修复（预计 1 周）
2. 补充测试覆盖（预计 1 周）
3. 进行完整回归测试（预计 1 周）
4. 至少 2 周稳定运行后再发布
